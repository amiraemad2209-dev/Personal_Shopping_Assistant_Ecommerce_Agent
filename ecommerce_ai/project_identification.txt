
#-----------------------------Personal Shopping Assistant (E-commerce Agent)----------------------#
#---------------------------------- وثيقة تعريفية وأكاديمية للمشروع ----------------------------#

1. مقدمة المشروع
1.1 اسم المشروع

Personal Shopping Assistant

مساعد تسوق شخصي يعتمد على تقنيات الذكاء الاصطناعي 
 والنماذج اللغوية الكبيرة 
 لمساعدة المستخدم في البحث عن المنتجات
 ، فهم احتياجاته، تحليل تفضيلاته، ومقارنة الخيارات المتاحة
 ، ثم تقديم توصيات شخصية مناسبة له.

لا يهدف المشروع إلى بناء  تقليدي يجيب عن أسئلة عامة، وإنما إلى بناء نظام ذكي
 يستطيع استخدام مجموعة من مصادر البيانات والأدوات
 لفهم من هو العميل وماذا يحتاج وما المنتجات المتاحة
 ، ثم اتخاذ خطوات مناسبة للوصول إلى توصية مفيدة.

===============================================================================================

2. خلفية المشكلة
2.1 مشكلة كثرة المنتجات

تحتوي المتاجر الإلكترونية الحديثة على أعداد كبيرة من المنتجات والخيارات والمواصفات.

عند رغبة المستخدم في شراء منتج، قد يواجه:

عددًا كبيرًا من النتائج.
مواصفات تقنية معقدة.
اختلافات بسيطة بين المنتجات.
صعوبة مقارنة المنتجات.
عدم معرفة المواصفات المناسبة لاحتياجاته.
صعوبة تحديد العلاقة بين السعر والجودة.
الحاجة إلى قراءة عدد كبير من صفحات المنتجات والمراجعات.

على سبيل المثال، إذا بحث مستخدم عن:
"Laptop"

فقد تظهر له مئات المنتجات.
لكن السؤال الحقيقي الذي يحتاج إلى إجابة ليس:
ما هي جميع أجهزة الـLaptop المتاحة؟
وإنما:

ما هو أفضل جهاز بالنسبة لاحتياجاتي وميزانيتي وطريقة استخدامي؟
وهنا تظهر الحاجة إلى نظام Personal Shopping Assistant.



2.2 مشكلة البحث التقليدي

يعتمد البحث التقليدي غالبًا على:

Keyword Search + Categories + Filters

مثال:
Search: Laptop


Filters:
- Price
- Brand
- RAM
- Storage
- CPU

ولكن المستخدم قد لا يعرف أصلًا:

ما حجم الـRAM الذي يحتاجه؟
هل يحتاج GPU منفصلًا؟
هل الأولوية للبطارية أم الأداء؟
ما الفرق بين المنتجات؟
هل المواصفات مناسبة لطريقة استخدامه؟

لذلك، فإن النظام المقترح يسمح للمستخدم بالتعبير عن احتياجاته بلغة طبيعية.

مثلًا:

"أنا بدرس Computer Science وبعمل Programming وبحب Gaming وميزانيتي حوالي 40 ألف جنيه."
ثم يقوم النظام بتحويل هذه الجملة إلى متطلبات يمكن استخدامها في البحث والتوصية.

3. الهدف الرئيسي للمشروع

الهدف هو بناء مساعد ذكي يستطيع:

فهم طلب المستخدم.
استخراج احتياجاته ومتطلباته.
الاحتفاظ بالسياق أثناء المحادثة.
تذكر بعض التفضيلات المهمة للمستخدم.
البحث في قاعدة بيانات المنتجات.
استخدام أدوات مختلفة حسب الحاجة.
ترتيب المنتجات المناسبة.
تقديم توصيات شخصية.
توضيح أسباب التوصية.
الاستفادة من Feedback المستخدم لتحسين التوصيات مستقبلًا.

4. أهداف المشروع التفصيلية
4.1 Personalization

تقديم توصيات تختلف من مستخدم إلى آخر.
مثلًا، نفس السؤال:

"رشحلي Laptop."

يمكن أن ينتج عنه إجابتان مختلفتان.

المستخدم الأول
Use Case:
Programming


Budget:
25,000 EGP


Priority:
Battery


Preference:
Portable device
المستخدم الثاني
Use Case:
Gaming


Budget:
50,000 EGP


Priority:
GPU Performance


Preference:
High performance

رغم أن السؤال نفسه، يجب أن تختلف التوصيات.

4.2 Context Awareness

يجب أن يفهم النظام المحادثة كسلسلة مترابطة.

مثال:

User: أنا عايز Laptop للـGaming.

ثم:

User: بس يكون مش غالي.

كلمة:

"مش غالي"

يجب أن ترتبط بالسياق السابق.

أي أن النظام يفهم:

Product:
Gaming Laptop


Constraint:
Affordable

وليس التعامل مع كل رسالة بشكل مستقل.

4.3 Persistent Personalization

يجب أن يستطيع النظام، في مراحل متقدمة، الاحتفاظ ببعض المعلومات المهمة عن المستخدم.

مثلًا:

Customer Profile


Interests:
- Gaming
- Programming


Preferred Brands:
- Lenovo
- Logitech


Budget Range:
30,000 - 40,000 EGP


Preferences:
- High Performance
- Good Battery


Dislikes:
- Expensive accessories
- Poor microphone quality

عند عودة المستخدم لاحقًا، يستطيع النظام استخدام هذه البيانات عند الحاجة.

8. Memory System

الـMemory عنصر أساسي لجعل النظام شخصيًا.

يمكن تقسيمها إلى مستويات مختلفة.

8.1 Short-Term Memory

تحتفظ بسياق المحادثة الحالية.

مثلًا:

User:
عايز Laptop.


Assistant:
هتستخدمه في إيه؟


User:
Programming وGaming.

عند إرسال المستخدم رسالة جديدة:

"البطارية مش مهمة."

يجب أن يفهم النظام أن الحديث ما زال عن:

Laptop
for Programming + Gaming
8.2 Window Memory

يتم الاحتفاظ بعدد محدد من الرسائل الأخيرة.

مثال:

Window Size = 4

يحتفظ النظام بآخر أربع رسائل فقط.

الميزة
بسيط.
سريع.
يقلل عدد الـtokens.
العيب

قد يفقد معلومات قديمة مهمة إذا كانت المحادثة طويلة.

8.3 Summary Memory

يتم تلخيص المعلومات المهمة بدل الاحتفاظ بجميع الرسائل.

مثلًا:

Original Conversation
User likes gaming.
User works as a programmer.
User prefers Lenovo.
User budget is around 40,000 EGP.
User does not care much about battery.
Summary
The customer is interested in gaming and programming,
prefers Lenovo products, has a budget around 40,000 EGP,
and prioritizes performance over battery life.
8.4 Hybrid Memory

يجمع بين:

Recent Messages
+
Conversation Summary
+
Persistent Customer Profile

ويمكن اعتباره النموذج الأنسب في المراحل المتقدمة.

10. Tools

الأدوات تسمح للنظام بتنفيذ وظائف حقيقية.

بدل أن يعتمد الـLLM على معرفته فقط.

يمكن تصميم الأدوات التالية.

10.1 Product Search Tool
product_search()
المسؤولية

البحث عن المنتجات بناءً على:

Category.
Budget.
Brand.
Specifications.
Availability.

مثال:

product_search(
    category="laptop",
    max_price=40000,
    use_case="gaming"
)
10.2 Product Details Tool
product_details()

تجلب المعلومات الدقيقة عن المنتج.

مثل:

Price
CPU
GPU
RAM
Storage
Display
Availability

وهذا مهم لتقليل مشكلة Hallucination.

لا يجب أن يخترع الـLLM:

سعر المنتج.
المواصفات.
التوافر.

بل يجب أن يحصل عليها من مصدر بيانات موثوق.

10.3 Recommendation Tool
recommendation()

تقوم بتحليل:

User Requirements
+
Customer Profile
+
Candidate Products

ثم ترجع أفضل المنتجات.

10.4 Feedback Analysis Tool
feedback_analysis()

مثال:

"الـHeadset صوتها ممتاز لكن الميكروفون سيئ."

يتم استخراج:

Positive:
- Audio quality


Negative:
- Microphone quality

ثم يمكن تحويل ذلك إلى Preference مستقبلية.

10.5 Save Preference Tool
save_preference()

وظيفتها حفظ المعلومات المهمة.

مثال:

Preference:
User dislikes poor microphone quality.

11. Agent System

الـAgent مسؤول عن تحديد الخطوة التالية.

بدل برمجة كل الاحتمالات يدويًا:

if search:
    ...
elif details:
    ...
elif recommendation:
    ...

يمكن للنظام العمل كالتالي:

User
 ↓
Agent
 ↓
Understand Request
 ↓
Decide Next Action
 ├── Search Tool
 ├── Product Details Tool
 ├── Recommendation Tool
 ├── Feedback Tool
 └── Direct Response
 ↓
Observe Result
 ↓
Continue if needed
 ↓
Final Answer

26. Multi-Tenancy

لأن النظام SaaS، يمكن أن يوجد:

Store A
Store B
Store C

وكل متجر له:

منتجات مختلفة.
عملاء مختلفون.
محادثات مختلفة.
إعدادات مختلفة.

لذلك يجب أن يكون النظام:

Multi-Tenant

مثال:

Store A
   │
   ├── Products A
   ├── Customers A
   └── Conversations A


Store B
   │
   ├── Products B
   ├── Customers B
   └── Conversations B

ويجب منع أي متجر من الوصول إلى بيانات متجر آخر.

27. Evaluation

يجب إنشاء مجموعة Test Cases.

مثال:

Test Case 1:
"عايز Laptop للبرمجة تحت 30 ألف."


Expected:
- Budget understood.
- Category understood.
- Products above budget excluded.
Test Case 2
"أنا قلتلك قبل كده إن البطارية مش مهمة."

يجب اختبار هل الـMemory تعمل بشكل صحيح.

Test Case 3
"إيه مواصفات المنتج X؟"

يجب التأكد من أن المعلومات تأتي من مصدر بيانات صحيح.

Metrics
Recommendation Relevance.
Tool Selection Accuracy.
Search Success Rate.
Hallucination Rate.
Response Latency.
Cost per Request.
User Satisfaction.

32. الخلاصة النهائية

Personal Shopping Assistant هو مشروع يمكن أن يبدأ كمشروع تعليمي لتطبيق مفاهيم:

LLMs
LangChain
Memory
Tools
Agents
Search
RAG
Persistent Memory

ثم يتطور تدريجيًا إلى نظام حقيقي يعتمد على:

Product Database.
Personalized Recommendation.
Customer Profiles.
Feedback Analysis.
Web Interface.
Merchant Dashboard.
Multi-tenancy.
Analytics.

ثم يمكن في النهاية تحويله إلى:

B2B AI SaaS for E-commerce Stores

والفكرة الأساسية للمشروع هي:

استخدام الذكاء الاصطناعي لفهم احتياجات العميل وتفضيلاته وسياقه، وربط ذلك ببيانات المنتجات الحقيقية، من أجل تقديم توصيات شخصية تساعده على اتخاذ قرار شراء أفضل.

وده يجعل المشروع مناسبًا جدًا كرحلة طويلة: من مشروع كورس → Portfolio Project → MVP → Production System → SaaS Product.
